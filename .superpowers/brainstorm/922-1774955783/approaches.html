实时进度可视化：两种实现方案

对比后端改动量和前端体验差异

方案 A：SSE 实时推送（推荐）
后端改动：
  • StoryboardService 中每完成一集，发布 Redis 事件
  • 扩展 SSE 端点推送集级事件
  • 新增 3 种事件类型
前端改动：
  • 移除阻塞性 spinner
  • 监听 SSE 事件，实时更新 UI
  • Episode/SegmentCard 增加加载态
SSE 事件流：
┌ episode:script_done (第1集剧本完成)
├ episode:storyboard_done (第1集分镜完成)
├ episode:grid_status (第1集九宫格 → generating)
├ episode:script_done (第2集剧本完成)
├ episode:grid_status (第1集九宫格 → generated)
└ ...
✅ 优点： 实时性最好，无延迟，利用已有 SSE 基础设施
⚠️ 缺点： 后端需改 2 个文件（StoryboardService + SSE Controller）
方案 B：生成期间轮询 Episodes API
后端改动：
  • 几乎不需要改后端
  • 现有 getEpisodes API 已返回每集状态
前端改动：
  • 移除阻塞性 spinner
  • 在生成期间启动轮询（3-5秒间隔）
  • Episode/SegmentCard 增加加载态
  • 需要处理"集尚未创建"的情况
轮询流程：
T+0s: GET /episodes → [] (空)
T+3s: GET /episodes → [{ep1: scriptDone}]
T+6s: GET /episodes → [{ep1: storyboardDone}]
T+9s: GET /episodes → [{ep1: gridGenerating}]
T+12s: GET /episodes → [{ep1: gridGenerating}, {ep2: scriptDone}]
└ ...
✅ 优点： 后端改动极小，只改前端
⚠️ 缺点： 3-5秒延迟，轮询开销，需要处理空状态
💡 推荐：方案 A（SSE 实时推送）

项目已有 SSE 基础设施（Redis Pub/Sub + ProjectSseController），只需扩展事件类型。 后端改动量不大（约 30 行代码），但用户体验提升显著——零延迟的实时进度反馈。
